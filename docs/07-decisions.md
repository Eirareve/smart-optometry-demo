# 技术决策记录

本文件使用轻量 ADR 记录会影响后续实现的重要决策。状态为“已接受”的决策仍应在获得厂家正式资料后复核。

## DEC-001：V0.1 定位为网页 Demo

- **状态**：已接受
- **Context**：当前需要先验证产品外观、操作流程和数据呈现，且尚未取得厂家设备接口资料。
- **Decision**：V0.1 只建设可在浏览器运行的网页 Demo；React + TypeScript 是后续实现阶段的计划技术选型，本次仅初始化文档，不初始化前端项目。
- **Reason**：网页 Demo 能以较低成本验证完整体验，并保留后续迭代空间。
- **Consequence**：当前不实现真实硬件通讯，也不声称已接入设备；未来开始开发时再建立工具链并补充准确命令。

## DEC-002：V0.1 使用 Mock Device

- **状态**：已接受
- **Context**：缺少厂家 API、SDK、协议、运行环境和错误码资料。
- **Decision**：V0.1 计划通过 `DeviceAdapter` 后的 `MockDeviceAdapter` 提供明确标记的模拟状态与模拟结果。
- **Reason**：在不虚构厂家能力的前提下，Mock 足以验证网页 Demo 的交互闭环。
- **Consequence**：Mock 行为不代表真实设备规范；获取正式资料后需要单独实现并验证真实适配器。

## DEC-003：未知 17 项采用扩展指标占位

- **状态**：已接受
- **Context**：所谓“17 项数据”尚无正式字段定义。
- **Decision**：仅使用 `metric_01`～`metric_17` 和“扩展检测指标 01”～“扩展检测指标 17”；使用可扩展集合承载，而非建立 17 个有医学语义的固定字段。
- **Reason**：中性占位可以避免错误医学解释，并降低正式字段到位后的模型改动范围。
- **Consequence**：Demo 不展示这些项的医学名称、单位、范围或诊断含义；后续依据正式文档建立独立映射。

## DEC-004：UI 与设备实现通过适配层解耦

- **状态**：已接受
- **Context**：厂家最终可能提供 DLL、SDK、串口、USB、TCP 或标准 Web API，目前接入形式未知。
- **Decision**：UI 只通过 Exam Service 和 `DeviceAdapter` 使用设备能力，不直接依赖 Mock 或任何厂家实现。
- **Reason**：稳定边界允许未来替换底层数据源，同时减少对页面和交互流程的改动。
- **Consequence**：需要维护统一契约、清晰错误状态和原始数据；真实接入路径在取得正式资料后决定。

## DEC-005：本地设备桥接服务是条件性方案

- **状态**：待资料确认
- **Context**：浏览器通常不能直接承载 Windows DLL 或多数私有硬件协议，但厂家实际能力未知。
- **Decision**：只有在正式资料确认需要 DLL、串口、USB 或 TCP 私有协议时，才采用 Local Device Bridge；若厂家提供标准 Web API，则重新评估。
- **Reason**：避免在接入方式未知时过早锁定技术实现。
- **Consequence**：桥接技术、接口和部署方式当前均为 `TBD`，不得按厂家既有能力对外描述。
